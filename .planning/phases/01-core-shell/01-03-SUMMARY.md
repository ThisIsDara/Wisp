## Deviations / Bug Fixes (the valuable part)

1. **Static module plugin must be linked explicitly.** `qt_add_library(wisp_qml STATIC)` + `qt_add_qml_module` builds a static plugin target `wisp_qmlplugin` whose registration objects never reach the exe unless linked. Without `target_link_libraries(wisp PRIVATE ... wisp_qmlplugin)` (and tst_shell likewise) the app fails at startup: `No module named "wisp" found` even though the module resources ARE embedded (qmldir loads from `:/qt/qml/wisp`, then `resolvePlugin ... wisp_qmlplugin not found`). Debugged via `QML_IMPORT_TRACE=1` — the import trace showed the qmldir loading but the static registration missing. Plan's `wisp_qmlmoduleplugin` target name didn't exist post-restructure; actual names: `wisp_qml` + `wisp_qmlplugin`.
2. **`qt_policy(SET QTP0001 NEW)` (CMakeLists.txt).** Moves module resources to `:/qt/qml/<Module>` — the canonical location the import system prefers. Without it, deployed apps (Qt DLLs beside the exe → relocatable-mode prefix resolution) fail to resolve the module while dev runs work.
3. **deploy.ps1 writes qt.conf** (`Prefix=.`, `Libraries=.`, `Plugins=plugins`, `Imports=.`, `QmlImports=qml`). windeployqt 6.11 does NOT emit one; required for clean import/plugin resolution from the deployed folder.
4. **Stale-build trap:** an incremental build left old module-in-exe artifacts (old qrc objects, `build/release/wisp/` dir, old registrations) that masked the static-plugin bug — the "working" raw exe was stale. `Remove-Item -Recurse -Force build` + full rebuild exposed the real failure. Lesson: after CMake restructure, wipe build dirs.
5. **deploy.ps1 ASCII-only** (PS 5.1): em-dash/smart quotes in `Write-Host` break parsing; all non-ASCII replaced, verified 0 non-ASCII bytes.
