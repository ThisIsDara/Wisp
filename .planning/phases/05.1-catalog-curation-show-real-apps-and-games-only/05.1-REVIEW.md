# Phase 05.1: Code Review Report — catalog-curation-show-real-apps-and-games-only

**Reviewed:** 2026-08-11
**Depth:** deep (cross-file: CurationRules → CurationStore → AppCatalog → ResultsModel → QML, plus diff range `24aab4e^..c6f68d4`)
**Files Reviewed:** 17
**Status:** issues_found

## Summary

The curation pipeline is well-architected: allowlist matching is pure and testable, the
store round-trips through a real temp INI, `markCurated` runs strictly after dedupe
(Pitfall 1 handled), hide/unhide preserve the query (Pitfall 3 handled), and the
`hiddenCount` NOTIFY wiring is complete and correct. The C++ core (marking, store,
seams) is solid — the two HIGH findings are in the new in-window context-menu overlay,
which has a broken dismissal catcher (anchored inside the wrong parent), clicks that
pass through the menu background and launch the app underneath, and no lifecycle
handling on hide/launch. One MEDIUM logic bug exists in `hideSelected`/`unhideSelected`
(duplicate-id rows). Matching correctness has two edge issues (apostrophe tokens,
short common-word tokens).

## HIGH (Critical)

### H-01: Context-menu dismissal catcher covers the wrong region — click-away dismissal is broken

**File:** `qml/MainWindow.qml:641-645`

**Issue:** `ctxDismiss` is a **child of `ctxMenu`** but anchored `anchors.fill: resultsView`
(a sibling of the menu). Anchors resolve against `resultsView`'s geometry but the result
is applied in the **parent's** (ctxMenu's) coordinate space, so the catcher's on-screen
region is shifted by the menu's own position: it covers
`[ctxMenu.x, ctxMenu.x + resultsView.width] × [ctxMenu.y + resultsView.y, …]`.
Since `resultsView.y ≈ 53` (44px field + 1px hairline + 8px `spaceSm`) and the menu is
36px tall (`menuItemHeight 28 + 2×spaceXs`), the catcher sits **entirely below the menu**.
Consequences:

- Clicks on the list **above/left of the menu** fall through to the delegate MouseAreas —
  the menu stays open and rows get **launched** (the list's `onClicked` → `launchIndex`).
- Clicks on the search field, `showHiddenRow`, and `addExeRow` never close the menu.
- Only the list sub-rectangle below/right of the menu's top-left actually dismisses.

The comment ("one transparent press anywhere else… closes the menu") describes intent,
not behavior.

**Fix:** Make the catcher a **sibling** of the menu (child of `surface`), declared after
the ListView, with `z` between the list and the menu (e.g. `z: 10`, menu stays `z: 20`):

```qml
// child of surface, sibling of ctxMenu, declared before ctxMenu:
MouseArea {
    id: ctxDismiss
    visible: ctxMenu.visible
    anchors.fill: resultsView
    z: 10
    onClicked: ctxMenu.closeMenu()
}
```

Remove the current child `ctxDismiss`. Because the catcher sits *under* the menu
(z 10 < z 20), the menu item still receives its clicks; everything else in the list
area dismisses.

### H-02: Clicks on the context-menu background pass through and LAUNCH the app underneath

**File:** `qml/MainWindow.qml:646-683`

**Issue:** The menu's visual layers are plain `Rectangle`s (no mouse handlers) — the
background (646-652) and the inner hover rectangle (653-657) — and the only clickable
`MouseArea` (`ctxItem`) covers just `104×20` inset by 8px margins. Qt Quick hit testing
passes clicks through visuals without handlers, so a click on the menu's 8px border
strip falls through to the delegate `MouseArea` **below the menu** → `onClicked`
(ResultsRow.qml:241-252) → `selectIndex` + `launchController.launchIndex(...)` — the
app the user was about to hide gets **launched** instead. With the right-click row
typically under the menu, this is a very plausible misclick.

**Fix:** Give the menu background its own click handler that closes the menu (cheap
belt-and-braces on top of H-01's catcher):

```qml
Rectangle {
    anchors.fill: parent
    color: Theme.surfaceSecondary
    radius: Theme.menuRadius
    border.width: 1
    border.color: Theme.border
    MouseArea { anchors.fill: parent; onClicked: ctxMenu.closeMenu() }
}
```

(And/or remove the inner item's 8px total inset so `ctxItem` covers the full menu.)

## MEDIUM (Warning)

### M-01: `hideSelected`/`unhideSelected` mark only the FIRST entry matching the id — duplicates diverge from persisted state

**File:** `src/core/ResultsModel.cpp:381-384` and `411-414`

**Issue:** The marking loop `break`s after the first match. Lnk rows are deduped by
displayName only — two shortcuts sharing one targetPath (per-user **and** all-users
Start Menu entries, or a launcher installed with two shortcut names, e.g. "Steam" and
"Steam - Games") have the **same id**. `hideSelected` on "Steam - Games" persists
`hide(id)` (which hides **both** on the next catalog rebuild), but in-session only the
**alphabetically first** matching entry is marked — which may be the *other* row. The
selected row stays visible, the unselected twin vanishes, and `hiddenCount()` (+1) no
longer matches the store state (rebuild → +2). Same for `unhideSelected`.

**Fix:** Mark every entry with the id (drop the `break`), matching `markCurated`'s
id-based semantics exactly:

```cpp
for (AppEntry &x : m_entries) {
    const QString xid = x.targetPath.isEmpty() ? x.aumid : x.targetPath;
    if (xid == id)
        x.hidden = true;   // no break — all same-id rows (catalog rebuild parity)
}
```

### M-02: Apostrophe tokens never match apostrophe-less store names

**File:** `src/core/CurationRules.cpp:10-27, 61-62, 79, 133`

**Issue:** `normalized()` collapses the apostrophe into a space, so
`"baldur's gate 3"` → `"baldur s gate 3"`, but the common GOG/EGS naming
`"Baldurs Gate 3"` → `"baldurs gate 3"` — **no match**, and the app is hidden by
default. Same for `"don't starve"` vs `"Dont Starve"` (line 79) and
`"no man's sky"` vs `"No Mans Sky"` (line 133). The allowlist's stated goal is that
"the user's real apps are covered"; these are exactly the user's measured apps.

**Fix:** Also test the apostrophe-stripped form of each token (cheap: build the variant
once in the `kCuratedTokens` pre-normalization):

```cpp
const QStringList kCuratedTokens = [] {
    QStringList tokens;
    for (const QString &name : kCuratedNames) {
        tokens.append(normalized(name));
        tokens.append(normalized(name).remove(QLatin1Char(' '))); // "baldur s gate 3" → "baldurs gate 3"
    }
    return tokens;
}();
```

(Or normalize entry names by removing apostrophes before the space collapse — one
variant, fewer tokens.)

### M-03: Context menu is never closed on hide/launch/query change — stale menu acts on the wrong row

**File:** `qml/MainWindow.qml:619-637` (menu), `793-809` (onVisibleChanged), `398` (onTextChanged)

**Issue:** `ctxMenu.visible` persists across window hide (nothing closes it in the
`onVisibleChanged` else-branch), across launches, and across query changes. Sequence:
right-click row 8 → menu opens → hotkey toggles window away/back (or user types) →
selection is reset to **row 0** by `onVisibleChanged` while the menu still shows the
stale "Hide"/"Unhide" label from `targetIsHidden` → clicking it hides **row 0**, not
the row the menu was opened on. Keyboard nav also works while the menu is open
(shell Keys handlers stay live), moving the selection under a stale menu.

**Fix:** Close the menu at every lifecycle point:

```qml
onVisibleChanged: {
    if (visible) { ... } else {
        ctxMenu.closeMenu()   // hide/launch dismissal
        ...
    }
}
onTextChanged: { ctxMenu.closeMenu(); resultsModel.setQuery(text); fileSearch.setQuery(text) }
```

And (robustness) have `openMenu()` re-assert `targetIndex` by re-reading the row's
`isHidden` instead of trusting the stale `targetIsHidden` capture.

## LOW (Info)

### L-01: Ctrl+H in show-hidden mode on a *visible* row writes a spurious "shown" override

**File:** `qml/MainWindow.qml:137-143`; `src/core/ResultsModel.cpp:398-419`

**Issue:** In show-hidden mode Ctrl+H always calls `unhideSelected()`, even when the
selected row is visible (not hidden). `unhideSelected` then persists `show(id)` for a
row that was never hidden. The override is inert today but pins the row visible against
**future** rule changes (allowlist shrink) and pollutes `curationShown` — and the
"Hide" action is unreachable via Ctrl+H in that mode. Fix: branch on the selected row's
`isHidden` (or make `unhideSelected` no-op when `!e.hidden`).

### L-02: `buildAppOrder` empty-query branch sizes `m_ranges` to `m_entries.size()`, not `m_order.size()`

**File:** `src/core/ResultsModel.cpp:109`

**Issue:** With hidden rows skipped, `m_ranges` is systematically **longer** than
`m_order`. Safe today (`data()` indexes by `idx.row() < m_order.size()`), but the same
phase fixed `setEntries` to `m_order.size()` (line 52) — the two sites are now
inconsistent, and any future `m_ranges.at(i)` loop over `m_order` would read stale
padding. Fix: `m_ranges = QVector<FuzzyMatcher::Result>(m_order.size());`.

### L-03: `CurationStore` never checks `QSettings::status()` / sync failures

**File:** `src/core/CurationStore.cpp:24-41`

**Issue:** A failed write or `sync()` (read-only INI, locked file, missing %APPDATA%)
silently discards the override — hide works in-session and vanishes on restart with no
trace. D-16 documents silent failure as policy; a `qWarning()` on `status() != NoError`
would make it diagnosable at zero UX cost.

### L-04: Ids containing `=` (legal in Windows paths) break the INI key round-trip

**File:** `src/core/CurationStore.cpp:28-31`

**Issue:** QSettings' INI parser splits key lines at the first `=`. A targetPath like
`C:\a=b\app.exe` writes a key that reads back truncated (`curationHidden/C:\a`), so the
hide is inert. The identity contract only guarantees slash-free. Rare, but a one-line
validation (reject ids containing `=`, `/`, `[`, `]` with a `qWarning`) closes it.

### L-05: Short common-word allowlist tokens widen visibility to unrelated apps

**File:** `src/core/CurationRules.cpp:44-204` (e.g. `word` 165, `edge` 159, `teams` 143,
`obs` 148, `signal` 142, `rust` 114, `portal` 126, `metro` 126, `halo` 72, `mafia` 88,
`prey` 124, `ark` 104, `sonic` 94, `spore` 103, `dayz` 113)

**Issue:** The word-boundary guard is doing its job (no prefix matches like
"Battle.networx"), but any app whose display name or exe basename contains one of these
words as a whole word is allowlisted — e.g. a generic "Signal Assistant", "Metro Tools",
or "Word Processor" app stays visible by default. Acceptable as an allowlist tradeoff
(checkpoint-approved), but worth a comment or a later review pass: single-word tokens
that are common English words are the false-positive driver.

### L-06: Zero-literal rule violations in new code

**File:** `qml/ResultsRow.qml:29` — `opacity: model.isHidden ? Theme.disabledOpacity : 1.0`
(the `1.0` is a raw visual literal; pre-existing `scale` uses the same pattern but new
code should follow the declared hard rule). `qml/MainWindow.qml:625` — `z: 20` magic
number (fix H-01 introduces `z: 10` anyway — promote both to `Theme.menuZ`/`Theme.menuDismissZ`).

### L-07: Stale comment

**File:** `qml/MainWindow.qml:10` — `width: Theme.windowWidth  // 672` — `windowWidth` is

**Files:** `tests/tst_model.cpp` (curation suite, 635-806), `tests/tst_catalog.cpp` (259-362)
