# Phase 05.1: Catalog Curation - Show Real Apps and Games Only - Research

**Researched:** 2026-08-11
**Domain:** Catalog pipeline curation (Qt6/C++/QSettings + Start Menu/UWP enumeration)
**Confidence:** HIGH (codebase pipeline + landscape), MEDIUM (exact default rule list — judgment calls from measured buckets)

## Summary

The user's complaint is a catalog-noise problem: 262 Start Menu .lnk resolve to only ~60 real apps/games, with ~200 noise entries in four measurable buckets (uninstallers, dev toolchains, Windows system utils, installer cruft). No major launcher solves this — PowerToys Run indexes everything with no blocklist ([VERIFIED: GitHub issue #3699 — the exact same complaint, open since 2020]), and the freedesktop-world precedent (Rofi `-drun-hide-desktop-files`) is a **blocklist + per-user overrides** model, not an allowlist. The pragmatic design: code-embedded default-hidden rules + a persisted per-row Hide/Unhide store + the existing "Add executable…" path as the allowlist escape hatch. Allowlist-only (hardcoding the ~60 apps) cannot generalize across machines; scoring-based curation needs usage history (LAUN-07, v2).

**Filter insertion point (the key threading decision):** the curation step belongs in `AppCatalog::onBuildFinished` on the **UI thread, after `dedupeLnkOverUwp`, before sort/swap** — implemented as a pure *marking* function (sets `AppEntry::hidden`), not a removal. Marking (vs. removing) keeps hidden entries in the snapshot so a "Show hidden" mode can reveal them for Unhide, and keeps the filter a single pure, testable function. It must run **after dedupe**: filtering before dedupe would let a hidden .lnk's suppressed UWP twin resurrect (e.g., hide .lnk "Calculator" → UWP "Calculator" appears). Curation runs on the UI thread, so the hide store is UI-thread-only (SettingsStore precedent — no mutex; the WR-01 LaunchHistory mutex is only needed if a worker ever reads it).

**User-added executables are structurally immune to curation:** added executables flow through `LaunchHistory::trackedExecutables` → `FileSearch` as `Source::File` rows, never through AppCatalog ([VERIFIED: codebase]). The "never silently drop a user-added app" constraint is satisfied by construction — and re-adding a hidden app via "Add executable…" visibly restores it. This is the documented escape hatch, not a bug.

**UWP policy:** there is no OS signal for "real" vs "junk" Store apps — `AppListEntry.DisplayInfo` exposes only name/description/logo ([VERIFIED: MS docs]), and the games-enumeration API is provisioning-restricted and unusable ([VERIFIED: MS docs]). Recommended: keep all launchable UWP apps (already junk-filtered by `isSkippable`), apply the name-based rules to them, and skip path-based rules (UWP rows have no path).

**Primary recommendation:** one curation seam on `AppCatalog` (`setCurationSource` returning the persisted hide/show id sets — the same std::function injection pattern as scanners), one pure `CurationRules` matcher in `src/core`, one `CurationStore` (SettingsStore/LaunchHistory makeSettings pattern, additive INI groups), model-level hide/unhide + "show hidden" toggle in `ResultsModel`, and a keyboard-first UI affordance (Ctrl+H on the selected row, mirroring the existing Ctrl+Enter/Ctrl+Shift+Enter pattern; footer row "Show hidden (N)" mirrors the pinned "Add executable…" row).

### Pattern 1: Curation as a Pure Marking Step in the Swap Pipeline
**What:** `AppCatalog::onBuildFinished` gains one step between dedupe and sort: a pure function that marks entries as hidden, using (a) static default rules and (b) the injected curation-source snapshot. Marking keeps hidden entries in the snapshot (Unhide + Show-hidden mode stay possible without rebuilds).
**When to use:** Always — this is the single home of "what is in the inventory" policy (D-08/D-09 domain).
**Why after dedupe:** filtering before dedupe resurrects the suppressed UWP twin of a hidden .lnk (dedupe drops UWP entries *because* a same-named .lnk exists; if that .lnk is hidden pre-dedupe, nothing suppresses the UWP twin).
**Threading:** runs on the UI thread (watcher completion); the curation source is a value-copy QSet read — no mutex needed (SettingsStore precedent). The worker never touches the store (avoids WR-01).
**Example (sketch, mirrors existing dedupe/sort style in AppCatalog.cpp):**
```cpp
// AppCatalog.h — the injection seam (same std::function discipline as Scanner)
struct CurationData { QSet<QString> hiddenIds; QSet<QString> shownIds; };
using CurationSource = std::function<CurationData()>;
void setCurationSource(CurationSource source);

// AppCatalog.cpp — onBuildFinished pipeline:
QVector<AppEntry> next = dedupeLnkOverUwp(result.entries);
markCurated(next, curationSnapshot());   // NEW — after dedupe, before sort
sortAlphabetical(next);
{ QMutexLocker locker(&m_snapshotMutex); m_snapshot = std::move(next); }
```
```cpp
// anonymous-namespace pure function (testable like dedupeLnkOverUwp):
void markCurated(QVector<AppEntry> &entries, const CurationData &data)
{
    for (AppEntry &e : entries) {
        if (e.source == AppEntry::Source::File)
            continue; // file rows never curated (added executables are File source)
        const QString id = e.targetPath.isEmpty() ? e.aumid : e.targetPath;
        if (data.shownIds.contains(id))
            continue; // explicit user override wins over default rules
        e.hidden = data.hiddenIds.contains(id) || CurationRules::matches(e);
    }
}
```

### Pattern 2: CurationStore — SettingsStore/LaunchHistory Persistence Precedent
**What:** A small class persisting two id sets to the existing wisp.ini as additive groups, using the `makeSettings` factory verbatim (LaunchHistory.cpp:24-30 / SettingsStore.cpp:11-17 — IniFormat + UserScope + "TID"/"wisp"; explicit path = QTemporaryDir test seam; `sync()` after every write).
**When to use:** Always — this is the established project pattern for user preference persistence (D-13/D-14). No registry, no new file format, no migration: the groups are additive and the INI already exists.
**Identity contract:** Lnk → `targetPath` (stable across .lnk renames; hides all shortcuts to the same exe — correct: same app); UWP → `aumid` (stable PFN!AppId); File rows are never curated. An id whose app was uninstalled is inert (nothing matches it next rebuild — "hidden app that gets uninstalled shouldn't break anything" holds by construction).
**Threading:** UI-thread-only like SettingsStore — **no mutex** (documented contract; if a worker ever reads it, add the LaunchHistory WR-01 QMutex discipline first).

### Pattern 3: Live Hide in the Model, Re-mark on Rebuild
**What:** The Hide action (QML → model) removes the row from `m_entries` immediately (query preserved — no D-08 query reset) and persists via the store seam. The 10-minute rebuild re-runs `markCurated` from the store, so nothing resurrects. If the hidden app is uninstalled, the next rebuild drops it naturally.
**When to use:** Hiding must not clear the user's in-progress query (a forced rebuild would reset it — D-08 `setEntries` resets the query). Both consumers (model live-remove, catalog re-mark) share one store — no dual filter logic.
**Searchable-when-hidden decision (discretion item, recommended):** hidden entries are **excluded from search results** by default (they are hidden from `buildAppOrder` entirely), but a "Show hidden (N)" mode reveals them dimmed with an Unhide affordance. This is the middle ground: the default list is clean, and hide mistakes are recoverable without editing the INI by hand.

### Anti-Patterns to Avoid
- **Filtering inside scanners (WinStartMenuEnumerator/WinUwpEnumerator):** embeds policy in the win/ firewall layer (violates ARCHITECTURE.md src/win pattern), pollutes `tst_enum`'s enumeration-fidelity contract, and breaks the dedupe ordering (UWP twin resurrection). Filter belongs in the catalog pipeline.
- **Hard removal at swap (no marking):** makes Unhide and Show-hidden impossible without rebuild-with-different-rules complexity; marking is one bool and enables both.
- **Filtering at ResultsModel/query time as the ONLY filter:** the model is a display/rank layer; inventory policy (rules) would leak in, and the empty-query alphabetical list would need its own filter copy. Keep rules in AppCatalog (marking), visibility in the model.
- **Reusing FuzzyMatcher for rules:** FuzzyMatcher is a subsequence *ranker* with a threshold ladder — wrong tool for semantic blocklist matching ("Uninstall" prefix, "Release Notes" token). Rules are plain case-insensitive prefix/token/path-segment checks. ([VERIFIED: FuzzyMatcher.h semantics — score() with tier ladder])
- **Persisting hide by displayName:** display names change (locale, app updates, .lnk description edits); `targetPath`/`aumid` are stable identity. Display-name rules are fine as *rules*; user hides must key on identity.
- **Curating File rows:** added executables (Source::File via `trackedExecutables`) must never be hidden — that is the locked escape-hatch constraint, enforced by the `source == File → continue` guard.

## Common Pitfalls

### Pitfall 1: UWP twin resurrection (filter order)
**What goes wrong:** Hide/rule-hide a .lnk entry and its same-named UWP entry appears in the list.
**Why it happens:** dedupe (D-10) suppresses UWP entries whose name collides with a .lnk *that exists at dedupe time*. Filter before dedupe removes the .lnk first, so the UWP twin survives dedupe.
**How to avoid:** run `markCurated` strictly after `dedupeLnkOverUwp` in `onBuildFinished`.
**Warning signs:** a test with scanner A = {Lnk "Calculator"}, scanner B = {Uwp "Calculator"}, hide-list containing the Lnk path → "Calculator" still present.

### Pitfall 2: QSettings key-shape corruption (WR-01 family)
**What goes wrong:** keys containing '/' create nested INI groups; keys containing unescaped special chars misbehave; cross-thread QSettings access crashes or returns stale data.
**Why it happens:** QSettings treats '/' as the group separator (LaunchHistory.cpp:19-21 documents the discipline); the catalog worker could touch the store if filtering moved to the worker.
**How to avoid:** identity keys = `targetPath` (already native separators, from parseLnk) or `aumid` (never contains '/'); normalize any user-typed path (LaunchHistory::normalize precedent); keep the store UI-thread-only and document it (SettingsStore precedent — if a worker ever reads, add the QMutex first).
**Warning signs:** hidden entries not surviving a rebuild; INI showing nested groups; QSettings assert in a worker thread.

### Pitfall 3: Query reset on hide (D-08 side effect)
**What goes wrong:** hiding a row mid-search clears the user's query and list.
**Why it happens:** a forced catalog rebuild emits `refreshed` → main.cpp `setEntries` → query reset (documented D-08 behavior).
**How to avoid:** hide = store write + live model removal (query preserved); do NOT force a rebuild on hide. The 10-min/next-show rebuild re-marks quietly.
**Warning signs:** typing "spo", hiding a result, and the field empties.

### Pitfall 4: Rule false positives on real apps
**What goes wrong:** a defensible token like "Help" or path fragment like "\qt\" hides a real app the user wants (e.g., Qt Creator under \Qt\Tools\, or a "Help" doc the user actually launches).
**Why it happens:** bucket-derived patterns are per-machine heuristics; the user's reference list is the acceptance oracle, not a universal truth.
**How to avoid:** keep the default rule list conservative and *documented per bucket*; every false positive is recoverable via Show-hidden → Unhide; add the specific exception to `shownIds` in tests where the user's reference list demands it.
**Warning signs:** acceptance pass on the user's machine shows a real app missing from the ~60-app reference list.

### Pitfall 5: "Hidden" as a security boundary
**What goes wrong:** assuming hiding an app prevents launching it.
**Why it happens:** curation is a UX filter — the app's exe and AUMID remain on disk and launchable by other means.
**How to avoid:** document in code + README: hide is *visibility curation*, never a security control. The model simply stops offering the row; `LaunchController` needs no changes.
**Warning signs:** (none — purely a documentation discipline.)

## Open Questions

1. **Should the "Show hidden (N)" footer row also appear when only *rule*-hidden entries exist (N > 0), or only for *user*-hidden?**
   - What we know: the rule list will hide ~200 entries on the user's machine, so N is large on day one; showing the footer immediately is expected and doubles as the feature's discoverability surface.
   - What's unclear: whether a persistent "Show hidden (262)" row is visual clutter vs. a useful power-user surface.
   - Recommendation: show it whenever N > 0 (rule- and user-hidden together); the acceptance checkpoint will judge. The row is one `visible: hiddenCount > 0` binding — cheap to flip during the UI pass.

2. **Ctrl+H vs. a hover-revealed "×" button on the row — which affordance wins for discoverability?**
   - What we know: the app is keyboard-first; rows have zero interactive chrome today (hover only paints background); Ctrl+Enter/Ctrl+Shift+Enter establish the modifier-key pattern on the shell Keys block.
   - What's unclear: mouse-only users won't discover Ctrl+H.
   - Recommendation: Ctrl+H primary (consistent, zero clutter); the "Show hidden (N)" footer provides the discovery path (it exists precisely when hidden entries do). A hover "×" is optional polish for the UI pass — defer.

3. **Does hiding a rule-hidden entry in Show-hidden mode write to `hiddenIds` (making it a *user* hide) or is the row simply un-hidden (written to `shownIds`)?**
   - What we know: two semantics — "hide explicitly" (redundant but durable) vs "unhide" (override). Ctrl+H on a visible row = hide; Ctrl+H on a dimmed row = unhide (shownIds). The marking function must check shownIds *first* so an override beats a rule.
   - What's unclear: none functionally — the semantics above are self-consistent; the planner just needs to encode them.
   - Recommendation: implement exactly that split; test the precedence (shownIds wins) explicitly.
